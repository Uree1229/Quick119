## 최종 사용자 흐름

1. 홈 **응급상황 접수 시작** → `/transport/` 채팅으로 바로 이동합니다. 기존 `/emergency`, `/voice-intake`도 303으로 이동합니다. `/emergency?step=patient` 등 기존 단계별 경로는 유지합니다.
2. 새 URL에서는 가상 접수 건을 한 번 생성합니다. `pid`가 있으면 같은 건을 복원합니다. 임의의 나이·증상은 생성하지 않습니다.
3. 처음에는 **시스템과 구급대원**만 대화합니다. 글이나 음성으로 작성하고 직접 전송합니다. 음성인식은 최종 결과만 초안에 추가하며 자동 전송하지 않습니다.
4. **지도/채팅 전환 버튼 왼쪽의 48px 원형 환자 아이콘**을 누르면 현재 화면 위에 환자 정보 팝업이 열립니다. 채팅·GPS 양쪽에서 열 수 있으며 저장된 항목과 구급대원 보고 원문을 함께 봅니다.
5. **병원 탐색 시작** → 같은 팝업에서 정보 최종 확인·수정 → **확인하고 탐색 시작** 순서입니다. 마지막 버튼을 누르기 전에는 후보 탐색을 실행하지 않습니다.
6. 서버에 확인한 정보를 저장한 뒤 후보를 조회합니다. 서버 정렬 순서에서 **최대 3곳**만 화면에 표시합니다. 후보 조회 자체는 수용 문의를 보내지 않습니다.
7. 대원이 후보에 수용 문의 → 병원이 수용 가능 응답 → 대원이 목적지 확정 순서로 진행합니다. **수용 응답만으로 병원이 채팅에 합류하지 않습니다.**
8. 목적지 확정 후 같은 대화에 병원이 참여하며, **확정 전에 구급대원이 보낸 기존 보고도 함께 열람**합니다. 이는 사용자가 명시적으로 선택한 동작입니다.

팝업은 native `dialog.showModal()`을 사용합니다. 상단 X·하단 닫기·Escape·배경 클릭으로 닫고, 저장 중에는 닫기를 막습니다. 내부만 스크롤하며 배경을 잠그고 종료 후 초점을 복원합니다. 팝업을 열면 음성 입력을 중단합니다. 폭은 최대 480px, 화면보다 작게 제한합니다.

## 데이터와 서버 연결

- `hospital_session_id: null`인 기존 개인 보고 계약을 사용합니다. 병원 확정 후에는 활성 병원 참여 구간으로 전송합니다. 다른 병원 합류 전에 쓴 초안은 확인 없이 새 참여자에게 보내지 않습니다.
- 시스템 답변은 저장된 메시지에서 도출한 **접수 확인**입니다. AI 진단·임상 분석이 아닙니다. 접수 확인의 ID가 안정적이어서 재조회·재시작 때 중복 표시하지 않습니다.
- 병원 과거 보고 공유는 기존 병원 API의 접근 허용을 먼저 확인합니다. 현재 확정 병원에만 이전 구급대원 보고를 추가하며 다른 병원 대화·다른 환자 기록은 제외합니다.
- 두 조회 사이에 새 시스템 이벤트가 생기는 경우를 수정했습니다. 이벤트 ID 교집합 대신 허용된 병원 참여 구간과 병원 ID로 필터링해 커서가 기록을 건너뛰지 않게 했습니다.
- 환자 정보 추출은 기존 `Quick119Voice.extract` 규칙을 재사용하는 검토용 제안입니다. 저장값·보고값 충돌은 자동 덮어쓰지 않고 원문 확인을 요구합니다. 연령대·상대 시각을 정확한 나이·시각으로 임의 변환하지 않습니다.
- 최종 확인은 `PATCH /api/patients/{pid}` → `GET /api/patients/{pid}/candidates` 순서입니다. 기존 `extra`와 편집 대상 밖 활력징후 키를 보존합니다.
- 후보 API는 진료 가능 항목·운영 제한·자원 정보를 확인하고 가상 이동시간 순으로 정렬합니다. 솔버 최적 배정이나 실제 수용 확정은 아닙니다. **상위 3개 제한은 프런트 표시 제한**이며 서버 응답을 3개로 줄인 것은 아닙니다.
- 초기 `/api/hospitals` 조회는 병원 기본정보용입니다. 자동 후보 탐색·자동 문의가 아닙니다.
- 미전송 초안, 결과 미확인 전송, 음성 입력 중에는 탐색을 막습니다. 새 보고나 환자 버전 변경 시 이전 후보로 문의하지 못하게 합니다.
- 수용 문의 이력이 생긴 뒤에는 이 화면의 정보 수정·새 탐색을 잠그고 조회와 기존 문의 처리만 제공합니다. 문의 후 정보 정정은 기존 서버의 별도 amendment 계약을 연결해야 합니다.
- 접수 기록·메시지는 서버 DB에 보존됩니다. 초안·재시도 요청·후보 목록·GPS 상태는 페이지 메모리에만 있으며 새로고침 시 복원하지 않습니다.

## 검증 결과의 범위

| 단계 | 확인한 범위 |
| --- | --- |
| 초기 접수 채팅 전환 | 서버·회귀 53개 통과. 그중 한 Python 검사가 Node 10개를 실행하며, 백엔드 7개도 53개에 포함됨. 숫자를 더해서 70개로 계산하지 않음 |
| 초기 브라우저 확인 | 접수 시작·개인 보고·새로고침 복원·수용·확정·이전 보고 공유·양방향 채팅·초안 확인 |

| 마지막 원형 버튼·팝업·3곳 제한 | JS 구문 확인, 팝업 열기·닫기·GPS에서 열기·성공 후 닫힘·실제 후보 카드 3개 확인. 전체 회귀검사는 반복하지 않음 |

**53개 통과는 마지막 팝업 수정 이후의 전체 회귀 결과가 아닙니다.** 기존 Chrome 드라이버 검사 6개는 초기 실행에서도 제외했습니다. 특히 `test_team_chat.py`의 실브라우저 경로와 `transport_harness.js`는 즉시 문의 카드가 생긴다는 이전 전제를 갖고 있어, 다시 실행하기 전에 최종 확인 단계와 PATCH/candidates 모의 응답을 반영해야 합니다.

실제 마이크 정확도, Android 설치 PWA, 실제 GPS·잠금·가상 키보드는 미검증입니다. 마지막 팝업의 390px 실측 검증도 완료했다고 주장하지 않습니다. 당시 브라우저 viewport 요청은 관측한 페이지 폭에 반영되지 않았습니다. 사용자는 테스트를 과도하게 늘리기보다 구현하고 띄우는 작업을 우선하도록 요청했습니다.

## 남은 작업과 주의점

1. 커밋/PR로 넘길 때 변경 파일과 신규 파일을 모두 포함하고, `.local/`, DB, 가상환경, 인증서·키는 포함하지 않습니다. 현재 브랜치에서 기능 단위 diff를 검토한 뒤 사용자가 요청한 범위로 게시합니다.
2. 위 두 브라우저 검사 기대값을 새 최종 확인 흐름에 맞춥니다. 필요한 검사만 실행하며 이전 53개 기록을 최종 상태 통과로 재사용하지 않습니다.

4. 문의 후 정보 정정/재탐색, 기존 환자 등록·별도 보고와 새 접수 연결, 실제 의료기관 ID 연결은 후속 작업입니다.
