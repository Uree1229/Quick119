# Android Chrome에서 QUICK119 설치·실행하기

## 현재 구현 상태

- 기존 FastAPI 서버에서 Manifest, Service Worker, 앱 아이콘을 제공합니다.
- `name: QUICK119`, `short_name: 퀵119`, `display: standalone`, `scope: /`입니다.
- 시작 URL은 `/?source=pwa`이며 기존 홈을 보여 줍니다. 응급 접수 → 음성 문진 → 환자 선택 흐름은 유지됩니다.
- 네이비 배경과 전용 192/512 PNG 아이콘으로 Android 기본 시작 화면을 구성합니다. 시작 화면의 구체적인 모양·지속 시간은 Android/Chrome이 결정합니다. 인위적인 로딩 대기나 입력 지연을 넣지 않았습니다.
- 설치한 아이콘으로 앱 범위 내 페이지를 열면 일반 Chrome 주소창 없는 standalone 화면을 사용하도록 요청합니다. 일반 Chrome 탭이나 외부 도메인은 별도 브라우저 화면이 될 수 있습니다.
- 설치 이벤트가 제공될 때만 설치 버튼을 표시합니다. 이벤트가 없어도 Chrome 메뉴 설치 방법을 안내합니다.
- `/pwa-check`에서 보안 컨텍스트·standalone 여부·음성 API 지원·마이크 장치 접근·GPS를 확인할 수 있습니다. 점검 버튼은 실제 사용자가 눌러야 권한을 요청합니다.
- 환자·문진·위치·응급실/API 응답은 SW 캐시에 저장하지 않고 동적 HTTP 응답에도 `Cache-Control: no-store`를 사용합니다. 오프라인에서는 개인정보 없는 안내와 119 전화 링크만 제공합니다.

설정 근거: [standalone 모드](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/display), [Android 시작 화면](https://web.dev/learn/pwa/web-app-manifest), [보안 컨텍스트와 SW](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers).

## 1. 같은 Wi-Fi에서 HTTP 화면 확인

프로젝트 루트 PowerShell에서:

```powershell
$env:QUICK119_ENV = "development"
$env:QUICK119_DB_PATH = "data/quick119-dev.db"
$env:QUICK119_EXTERNAL_API = "0"
$env:QUICK119_LOAD_ENV = "0"
.\.venv\Scripts\python.exe -m uvicorn main:app --host 0.0.0.0 --port 8000 --no-access-log
```

`ipconfig`로 PC의 Wi-Fi IPv4를 확인합니다. PC와 Android를 같은 신뢰할 수 있는 Wi-Fi에 연결하고 휴대폰에서 `http://PC의IPv4:8000`을 엽니다. Windows 방화벽은 개인 네트워크의 해당 포트만 허용합니다. 작업 후 Ctrl+C로 종료합니다.

이 방법은 화면·터치·이동 확인용입니다. PC의 LAN IP에 HTTP로 접속하면 설치·Service Worker·마이크·GPS의 보안 조건을 충족하지 않습니다. 휴대폰의 `localhost`는 PC가 아닙니다. 실데이터를 입력하지 마세요.

## 2. 같은 Wi-Fi에서 신뢰되는 HTTPS로 준비

현재 프로젝트에는 서버 인증서나 개인키를 포함하지 않습니다. 아래는 사용자가 직접 준비하는 개발용 절차이며, 이번 작업에서 인증서 생성·신뢰 설치·방화벽 변경은 수행하지 않았습니다.

### 인증서 준비

PC에 [mkcert 공식 Windows 설치 안내](https://github.com/FiloSottile/mkcert#installation)를 따라 mkcert를 설치합니다. 신뢰할 개발 CA 설치는 시스템 신뢰 설정을 변경하므로 개발용 PC·시험 기기에서만 사용합니다.

아래의 예시 IP를 `ipconfig`에서 확인한 실제 PC의 Wi-Fi IPv4로 바꿉니다.

```powershell
New-Item -ItemType Directory -Path .\certs -Force
$pcIp = "192.168.0.10"
mkcert -install
mkcert -cert-file .\certs\quick119.pem -key-file .\certs\quick119-key.pem localhost 127.0.0.1 "::1" $pcIp

$caDirectory = mkcert -CAROOT
Copy-Item -LiteralPath (Join-Path $caDirectory "rootCA.pem") -Destination .\certs\quick119-dev-ca.crt
```

휴대폰으로 옮기는 파일은 **공개 CA 인증서 `quick119-dev-ca.crt`만**입니다. Android 보안/인증서 설정에서 개발 CA로 설치합니다. 제조사·Android 버전에 따라 메뉴 이름이 다릅니다. `rootCA-key.pem`, `quick119-key.pem`은 휴대폰·저장소·공유 서비스에 전달하지 않습니다. CA와 서버 개인키는 Git에서 제외됩니다. 테스트를 마치면 시험 기기에서 개발 CA를 제거합니다.

PC의 IP가 바뀌면 새 IP가 포함된 서버 인증서를 다시 발급하고, 실행 명령의 주소도 변경해야 합니다. 인증서 경고를 무시하거나 Chrome의 보안 기능을 끄는 방법은 사용하지 않습니다.

### 개발 HTTPS 실행

```powershell
.\scripts\start-https.ps1 -CertFile .\certs\quick119.pem -KeyFile .\certs\quick119-key.pem
```

스크립트는 기존 `.env`·`emergency.db`를 사용하지 않고 별도 개발 DB, 실제 외부 API 비활성화, 접근 로그 비활성화로 실행합니다. 기본 바인딩은 `0.0.0.0:8443`입니다. Windows 방화벽은 해당 개인 네트워크의 8443 포트만 허용합니다.

Android Chrome에서 `https://실제PC의IPv4:8443/pwa-check`에 접속합니다. 인증서 경고 없이 열리는지와 ‘보안 컨텍스트: 예’를 먼저 확인합니다. 오류가 있으면 인증서의 IP·개발 CA 설치·PC/휴대폰 날짜·Wi-Fi 연결을 점검합니다. 이 절차는 신뢰할 사설망과 합성 데이터 전용이며, 인증 없는 개발 서버를 인터넷에 공개하는 절차가 아닙니다.

## 3. Android 홈 화면에 설치

1. 같은 HTTPS 주소의 `/` 홈을 Android Chrome에서 엽니다.
2. 표시되는 ‘홈 화면에 퀵119 설치’ 버튼 또는 Chrome 메뉴의 ‘홈 화면에 추가’/‘앱 설치’를 선택합니다. 메뉴 명칭과 설치 가능 시점은 버전·기기 상태에 따라 달라집니다.
3. 설치 완료 후 Chrome 탭 대신 홈 화면의 퀵119 아이콘으로 실행합니다.
4. 네이비 시작 화면·앱 아이콘, 주소창 없는 앱 화면, 홈·접수·환자 선택으로 이동 시 앱 범위 유지를 확인합니다. 이름 표시는 OS가 Manifest의 name/short_name 중에서 선택할 수 있습니다.
5. `/pwa-check`에서 ‘standalone 앱 화면’ 표시를 확인합니다. 일반 브라우저 탭으로 표시되면 설치한 아이콘으로 재실행하고 단순 바로가기와 PWA 설치를 구분합니다.

## 4. GPS·마이크·직접 입력 실기기 점검

- 일반 Chrome 탭과 설치 앱을 각각 확인합니다.
- `/pwa-check`의 마이크 버튼은 장치 접근 후 스트림을 즉시 종료합니다. 녹음·업로드·저장하지 않으며 음성인식 성공을 의미하지 않습니다.
- 음성 문진에서 실제 한국어 인식·중지·직접 입력·분석·환자 선택 이동을 별도로 확인합니다. 브라우저 음성 서비스는 네트워크와 브라우저 제공자 서버에 의존할 수 있어 합성 문장만 사용합니다.
- 음성 API가 없거나 권한이 거부되면 직접 입력으로 진행합니다. HTTP 환경에서도 직접 입력은 남아 있습니다.
- GPS 점검 버튼은 정확도만 표시하고 좌표를 서버/저장소로 보내지 않습니다. 기존 주변 응급실 화면은 버튼을 누른 뒤 위치를 취득하고 FastAPI에 전달합니다. 개발 모드에서는 실제 병원 API가 비활성화되어 조회 제한 안내가 나오는 것이 정상입니다.
- 권한 허용·거부·시간 초과·설정 변경 후 재시도와 키보드/가로 화면을 점검합니다. HTTPS 연결만으로 권한 허용이나 음성 서비스 성공을 보장하지 않습니다.

## 5. 캐시·업데이트와 보안

- 캐시 이름은 `quick119-static-v1`입니다. 정적 CSS/JS·아이콘·개인정보 없는 오프라인 파일 9개만 설치 시 저장합니다.
- 모든 일반 HTML·환자·접수·위치 쿼리·API·POST는 저장하지 않습니다. 브라우저가 오프라인이면 네트워크 내비게이션에 안전한 안내만 반환합니다.
- PC Chrome의 Android 원격 디버깅으로 Application → Cache Storage를 확인합니다. 환자명·증상·좌표·병상 응답이 없어야 합니다. 오프라인에서 과거 병상 정보를 반환하지 않는지 확인합니다.
- 업데이트는 진행 중 문진을 강제 새로고침하지 않습니다. 안내가 나오면 입력을 마친 뒤 모든 퀵119 창을 닫고 다시 실행합니다. 정적 파일을 변경하는 다음 개발자는 `sw.js`의 캐시 버전도 변경해야 합니다.
- 실제 인터넷 서버 배포 전에는 환자별 접근 제어·로그인/세션·CSRF·민감 URL/로그·쿠키·HTTPS 프록시·인증서 보안 점검이 필요합니다. 현재 환자 접근 인증은 미구현이므로 공개 배포하지 않았습니다.

## 검증 상태와 명령

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

PC Chrome을 사용할 수 있는 Windows에서는 임시 Chrome 프로필과 loopback 테스트 서버를 사용합니다. 실제 DB와 외부 병원 API는 사용하지 않습니다. Chrome이 없으면 브라우저 항목은 skip으로 기록됩니다.

현재 PC 자동 검증: 기존 라우트 회귀, Manifest와 PNG 규격, 민감 응답 no-store, SW 허용 목록·오프라인·업데이트 정책, 실제 SW 등록, 민감 요청 후 캐시 불변성, 360/375/390/412/430px에서 홈·환자 선택·권한 점검 화면의 가로 넘침 여부.

**미검증:** Android 실기기 설치·시작 화면·주소창·음성/GPS·신뢰되는 HTTPS 인증서 연결, 나머지 기존 화면 전체의 모바일 배치. PC loopback HTTP는 개발용 보안 컨텍스트이며 실제 HTTPS/Android 검증을 대신하지 않습니다.

## GPS 기반 실시간 경로 안내

기존 Leaflet 지도와 `POST /api/routes/car` → 카카오모빌리티 자동차 길찾기 연동을 재사용합니다. 병원 상세정보의 자동차 경로 버튼으로 응급실을 선택하고 경로를 확인한 뒤 **실시간 안내 시작**을 누릅니다. 시작 전에는 연속 GPS 추적을 하지 않습니다.

- 현재 위치 마커는 유효한 GPS 측정마다 이동합니다. 기존 경로선과 목적지는 유지합니다.
- 지도를 드래그하거나 터치·확대·키보드 조작하면 자동 중앙 이동을 해제합니다. **내 위치 따라가기**로 다시 활성화합니다. 재탐색도 사용자가 보고 있는 지도 영역을 강제로 바꾸지 않습니다.
- 거리·시간은 마지막 경로 API 계산 위치 기준이며 마지막 계산 시각을 함께 표시합니다. GPS 측정마다 API를 호출하거나 초 단위로 시간이 줄어드는 방식은 아닙니다.
- 일반 갱신은 거리·시간을 갱신하고 경로선을 유지합니다. 이탈이 연속 확인되면 새 경로선으로 교체합니다. 도로 좌표가 없는 응답에서는 출발지·목적지를 표시하고 다음 유효한 재계산에서 경로를 다시 요청합니다.
- 목적지 근처에서 정확한 위치가 연속 확인되면 도착 안내 후 추적을 종료합니다. 이는 실제 응급실 출입구 도착을 보장하지 않습니다.
- 안내 종료·목적지 변경·화면 숨김·페이지 이탈 시 GPS watch, 감시 타이머와 진행 중인 브라우저 요청을 정리합니다. 이전 GPS 콜백이나 API 응답은 새 화면에 반영하지 않습니다.
- **화면 꺼짐·잠금·앱의 백그라운드 전환으로 GPS 추적이 중단될 수 있습니다.** 화면 숨김 이벤트가 오면 안내를 종료합니다. 복귀 후 사용자가 다시 시작해야 하며 자동으로 재개하지 않습니다. Android가 프로세스를 먼저 중단하면 이벤트 실행 자체도 보장되지 않습니다. 백그라운드 내비게이션은 지원하지 않습니다.
- 위치 권한 거부 시 안내를 종료합니다. 일시적인 수신 실패·시간 초과는 화면에 알리고 다음 수신을 기다립니다. 유효한 GPS가 30초 이상 없으면 위치와 계산값이 오래되었을 수 있다고 알립니다.
- 경로 API 오류 시 마지막 경로·계산값을 유지하고 오류를 표시합니다. 재시도 간격은 20초부터 최대 120초까지 늘어납니다. 유효한 위치 수신과 갱신 조건이 있어야 재시도하며, 오류만으로 반복 요청하지 않습니다.
- 일반 자동차·교통 상황 기준 예상값입니다. 구급차 긴급주행 시간을 보장하지 않습니다. 음성 내비게이션과 Android 네이티브 앱 전환은 포함하지 않습니다.

### 갤럭시 점검 시 조정할 상수

`static/car-routes.js`의 `NAV`에 모아 두었습니다. 거리 단위는 m, 시간 단위는 ms입니다.

| 항목 | 초기값 / 판단 |
|---|---|
| 유효 GPS 정확도 | 50m 이하, 측정 후 15초 이내 |
| API 최소 간격 | 10초, 동시 요청 1개 |
| 이동에 따른 갱신 | 마지막 성공 계산 위치에서 100m 이상 이동 |
| 시간에 따른 갱신 | 마지막 요청 후 30초 이상이며, `max(25m, 현재 정확도 + 마지막 계산 정확도)` 이상 이동 |
| 경로 이탈 | 경로 선분까지 거리가 `max(80m, 현재 정확도 × 2)` 초과 |
| 이탈 확인 | 최소 2초 간격의 유효 측정 3회 연속 |
| 도착 확인 | 목적지 반경 40m, 정확도 25m 이하, 유효 측정 3회 연속 |
| 연속 판단 초기화 | 정확도 부족·위치 오류·위치 튐·조건 미충족, 또는 측정 간격 15초 초과 |
| 위치 튐 | 이전 측정부터 70m/s로 이동 가능한 거리와 두 측정의 정확도 합보다 큰 이동은 무시 |

30초 경과만으로 정지 상태에서 API를 호출하지 않습니다. 이탈 재탐색에도 API 최소 간격과 오류 재시도 대기를 적용합니다. 도착·이탈 판단은 실제 기기와 도로 환경에 따라 상수 조정이 필요합니다.

### 모의 GPS 자동 검증

프로젝트 루트에서 다음을 실행합니다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_app.py -v
```

`tests/car_navigation_harness.js`는 실제 Leaflet과 실제 안내 스크립트에 모의 GPS·시간·API를 연결합니다. 정지·미세 흔들림·정상 이동·낮은 정확도·위치 튐·연속 이탈·도착·지도 따라가기·API 실패·종료 후 늦은 응답·백그라운드 전환을 검증합니다. 외부 경로 API와 배경 타일 요청은 하지 않습니다. 기존 통합 테스트는 임시 DB와 가상 응급실을 사용하며 실제 `.env`와 환자 DB를 읽지 않습니다. Desktop Chrome이 설치되어 있어야 브라우저 검증이 실행됩니다.

### 갤럭시 Chrome / 설치형 PWA 직접 확인 항목

초기에는 실제 운행 대신 모의 위치를 사용하고, 두 실행 환경에서 각각 확인합니다.

1. 신뢰되는 HTTPS에서 응급실 선택 → 경로 확인 → 안내 시작이 정상 동작하는지, 시작 전에 연속 추적하지 않는지 확인합니다.
2. 위치 권한 허용·거부, Android 위치 서비스 끄기/켜기, 실내의 낮은 정확도에서 상태 안내와 재시작을 확인합니다.
3. 모의 위치를 순차 이동시켜 마커·남은 거리·예상시간·갱신 시각과 API 호출 간격을 확인합니다. 정지 상태의 30초 경과로 요청이 늘지 않는지 확인합니다.
4. 지도를 직접 이동·확대한 뒤 자동 중앙 이동이 멈추고, 따라가기 버튼으로 복원되는지 확인합니다.
5. 한 번의 경로 이탈·위치 튐으로 재탐색하지 않는지, 연속된 이탈에서만 경로를 교체하는지 확인합니다.
6. 목적지 근처 한 번의 측정으로 도착하지 않고, 정확한 연속 측정 후 도착 안내와 종료가 이루어지는지 확인합니다.
7. 안내 중 종료 버튼·목적지 변경·뒤로가기·홈 화면 이동·화면 잠금을 각각 확인합니다. 복귀 후 자동 추적이 재개되지 않고, 다시 시작할 수 있어야 합니다.
8. 네트워크 끊김·복구 시 마지막 경로가 유지되고, 오류와 마지막 계산 시각이 보이는지 확인합니다.
9. 작은 화면과 가로 화면에서 버튼·지도에 가로 넘침이 없는지, 환자 등록·음성 입력·응급실 목록·병상 정보·PWA 설치가 유지되는지 확인합니다.

브라우저에서 요청을 중단하더라도 서버가 이미 카카오로 전달한 요청은 완료될 수 있습니다. 종료 이후 새 요청과 오래된 응답 반영을 차단하며, GPS·경로의 DB/PWA 캐시 저장은 추가하지 않았습니다. 실제 카카오 인증·요금·할당량·교통 결과 및 갤럭시의 GPS 품질은 모의 테스트만으로 검증되지 않습니다.
